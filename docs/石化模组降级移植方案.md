# 石化模组（Petrification）多版本降级移植总方案

> 目标：把只读原项目「石化模组原项目可以看不可更改-forge-26.2-65.1.0」（MC 26.2 / Forge 65.1.0，v2.1.0，58 个 Java 文件约 6900 行）
> 按版本从高到低逐步移植到本目录全部 14 个 `*-mdk`，**禁止改动原项目**，每版以 `gradlew compileJava` 实际编译通过为验收，功能全部保留。

## 一、移植链（相邻版本 = 上一移植基准，把每次 API 差异降到最小）

```
源(26.2/65.1.0)
 └→ 26.1.2/64.1.0   (FG7, JDK25)          ← 最高降级目标，先做
    └→ 1.21.11/61.2.0 (FG7, JDK21)
       └→ 1.21.10/60.1.0 (FG6, JDK21)
          └→ 1.21.8/58.1.0
             └→ 1.21.5/55.1.0
                └→ 1.21.4/54.1.14
                   └→ 1.21.3/53.1.0
                      └→ 1.21.1/52.1.0
                         └→ 1.21/51.0.33
                            └→ 1.20.6/50.2.0
                               └→ 1.20.4/49.2.0   （以下进入"无数据组件"时代）
                                  └→ 1.20.2/48.1.0
                                     └→ 1.20.1/47.4.10（旧式 SimpleChannel 网络）
                                        └→ 1.19.2/43.5.0
```

关键分界线：
- **1.20.5 起**才有 Data Components（本目录 1.20.6/50.2.0 及以上直接沿用组件存储）。
- **1.20.4 及以下**（1.20.4/1.20.2/1.20.1/1.19.2）无数据组件 → 见第六节存储降级设计。
- **≤1.20.1**（1.20.1/1.19.2）Forge 网络还是 SimpleChannel + IndexedMessageCodec，Payload 类需整体改写为旧式消息。
- **1.21.11/26.1.2** 两个 mdk 是 FG7（gradle 9.5 / `minecraft.dependency(...)` / `register('client')`、mods.toml 写死字面值），
  **1.21.10 及以下**都是 FG6（gradle 8.x / `minecraft "net.minecraftforge:forge:..."` + reobf、mods.toml 用 `${...}` 占位符由 gradle.properties 展开）。
- 所有 mdk 均用 **official（Mojang）映射**。

## 三、每个版本的执行流程（标准动作，逐版本重复）

1. **重置源码**：删 `src/main/java`、`src/main/resources`，从"上游移植基准目录"整体复制 Java 与 resources（基准 = 上一个已通过版本的结果；第一个目标 26.1.2 的基准 = 原项目只读目录）。同时复制 `logo.png`。
2. **工程元数据适配**：
   - FG6：改 `gradle.properties` → `mod_id=petrification`、`mod_name=Petrification`、`mod_version=2.1.0`、`mod_group_id=com.xiong.petrification`、`mod_authors=Xiong & Qianwen`、`mod_license=All Rights Reserved`、mod_description（注明对应 MC 版本）；其余（forge/mc/mapping 版本与范围）保持 MDK 模板。
   - FG7：改 `build.gradle` 的 `version`/`group`、`runs` 里 `forge.enabledGameTestNamespaces` 与 data 的 `--mod` 为 `petrification`；直接改字面 `mods.toml`。
   - mods.toml 三处随目标调整：`loaderVersion`、forge 依赖 `versionRange`、minecraft 依赖 `versionRange`（见上表），并把 description 首句的 MC 版本号改为目标。
3. **编译**：`.\gradlew.bat compileJava --console=plain`（首次会下载该版 Forge+MC+FG，慢属正常）。循环修错误直到通过。
4. **记录差异**：把该版本相对上游的关键 API 差异摘要记录在第七节下，作为后续版本提示。
5. 编译通过后进入下一版本；全部完成后视需要 `build` 出 jar 复核 resources。

### ⚠️ 重要经验（26.1.2 实践教训）
- 本机存在 VS Code Java/Gradle 扩展的**自动构建**（vscode-gradle 服务与零星 runClient 进程），会与命令行 Gradle **并发抢写 mavenizer 缓存/build 目录**，曾导致 mavenizer EOF、缓存假损坏、以及 **build-cache 恢复过期 class 输出**造成的"编译错误假象"（同一份引用 EntityTypes/cubemob 的代码时而通过时而报错）。
- **每次编译务必加 `--no-build-cache`**（gradle.properties 开了 `org.gradle.caching=true`，恢复旧输出会掩盖真错误）；配置缓存出怪象时再加 `--no-configuration-cache`。必要时先 `gradlew --stop` 并清理项目 `build`/`.gradle`。
- 排查"某类是否存在"不要只信 javac 单文件增量结果；用 `clean` 或对 decompile 源码 jar（全局缓存 `...\mavenizer\caches\forge\.global\mcp\<ver>\...\decompile\decompile.jar`）做 `jar tf` 判断最权威。
- 首次跑通一个版本后，该版 MC/Forge 已在全局 mavenizer 缓存，后续反复编译只要几秒；但**每个新 MC 版本第一次**仍需 ~10-20 分钟下载+反编译。



## 四、本工程环境事实
- 本机已装 JDK 17.0.12 / 21.0.11 / 22.0.2 / 25.0.2；FG6(≤1.20.4)=17、FG6(1.20.6+)与FG7(1.21.11/26.1.2)=21/25 均可用。

## 五、跨版本 API 差异提示（编译导向，先记已知重点）
- 26.x 特有：方块实体/存档序列化改为 `ValueOutput/ValueInput`、`TagValueOutput/TagValueInput`、`loadWithComponents(...)`（26.1/26.2）；block 方法签名如 `updateShape(... ScheduledTickAccess ticks ...)`、`getDrops()` 返 List、`useWithoutItem`、`getCloneItemStack(..., boolean includeData)`。降到 1.21.x 时要改回 `CompoundTag + HolderLookup`、旧 block/use 签名。
- 类名：26.x 里 `ResourceLocation` 类被映射为 `Identifier`（待编译确认究竟从哪个版本改名，编译报错即知）。
- 1.21.x 各小版本：菜单/容器、物品 tooltip（`TooltipDisplay`/`appendHoverText` 演变）、`TooltipContext`、Creative tab 事件、`DataComponents` 内置组件键（如 `POTION_CONTENTS`）迁移、`EntityType.getDefaultLootTable`、渲染注册等，全部以编译错误驱动。
- 方块注册从需 `MapCodec`（`codec()`）的版本开始才有该要求；早期版本忽略即可。
- 1.20.2+ payload 网络：`ModNetwork` + `PayloadRegistrar`/`ClientPayloadHandler` 等仅在 1.20.2~1.21.x 存在，26.x 沿用；≤1.20.1 需整体改写。

## 六、预-1.20.5 数据存储降级设计（1.20.4/1.20.2/1.20.1/1.19.2）
原代码把两种"大对象"数据放进 ItemStack Data Component：
- `StatueComponent`（38 字段实体快照）→ 组件键 `STATUE_DATA`；
- `StructureStatueData`（整栋建筑调色板+打包坐标+方块实体 NBT）→ `STRUCTURE_STATUE_DATA`；
并常驻方块实体字段、经 NBT 存档、随 update tag 同步到客户端供渲染。另在创造页用 `DataComponents.POTION_CONTENTS` 造药水。

### 6.1 数据组件 → 物品/方块实体 NBT（等价替换，不损失功能）
设计原则：**保留 record 类与其 `CODEC`**（RecordCodecBuilder/Codec 在旧版同样存在，可用 `NbtOps.INSTANCE` 把它编码/解码成 `CompoundTag`），只替换"存放介质"：
1. 新增工具 `component/ComponentNbtUtil`（或直接散改）：
   - `T <T> Optional<T> getFromStack(ItemStack, Codec<T>, String key)`：读 `stack.getOrCreateTag().getCompound("petrification").get("key")` → `CODEC.parse(NbtOps.INSTANCE, tag)`。
   - `void setToStack(ItemStack, Codec<T>, String key, T)`：反向写入。
   - `T <T> getFromTag/setToTag(CompoundTag ...)` 供方块实体存档与 update tag 复用。
2. 原调用点 `stack.get(KEY)` / `stack.set(KEY,v)` / `stack.has(KEY)` → 工具方法。涉及文件（已盘点）：
   - `item/StatueBlockItem`（放置时把组件写入 BE、tooltip、改名）
   - `item/MiniStructureBlockItem`、`item/StructureCoreItem`
   - `block/StatueBlock`（掉落/clone 时把 BE 数据封进物品）、`block/MiniStructureBlock`
   - `handler/ModRecipeHandler`（识别雕像→分解配方等）、`handler/RestorationHandler`（还原/涂蜡时读写组件）
   - `util/MaterializationHelper`（生物→雕像时写入 item）
   - `client/StatueSpecialRenderer`、`client/StatueSulfurCubeRenderer`（从实体/物品读雕像数据做实体渲染）
3. 四个方块实体的存档：`saveAdditional/loadAdditional/getUpdateTag` 由 26.x 的 `ValueOutput/ValueInput` 改回旧式 `CompoundTag + HolderLookup.Provider`，内容仍是把组件 NBT 存进 BE 自身 tag；`getUpdateTag` 返回带数据 tag（保证客户端 BE 有字段，渲染器才能画）。
4. 药水：≤1.20.4 用物品 NBT 键 `"Potion"`（`PotionUtils.setPotion(stack, potion)`）+ 酿造注册 API 旧式（1.20.5 后改为数据驱动/新注册）；创造页填 `PotionContents` 处改为旧 API。
5. 移除/条件编译 `registry/ModDataComponents`（该版本无 DataComponent 注册）。

### 6.2 网络降级
- 1.20.4 / 1.20.2：payload 机制尚在（1.20.2+ 引入），只做包体读写的小幅适配。
- 1.20.1 / 1.19.2：`network/*Payload` + `ModNetwork` 全部改写为 `SimpleChannel.registerMessage` 风格（encode(FriendlyByteBuf)/decode/handler），包结构保持同名字段。

### 6.3 保存与升级兼容
- 不承诺跨 MC 版本存档互通（各版本各存各的）。
- 沿用原版语义：方块实体 NBT/物品 tag 用统一子键名（如 `petrification:StatueData`），与 26.x 的 `StatueData` 键尽量一致，减少困惑。

### ⚠️ IDE 回写覆盖警告（1.21.11 实战新增）
- 若目标工程的 build.gradle/源码文件正被 IDE（VS Code/IntelliJ）打开且缓冲区未刷新，**外部修改可能被编辑器旧缓冲回写覆盖**（本次 build.gradle、MiniStructureRenderer、data/* 均被回退过）。

### ✅ forge-1.21.8-58.1.0（已完成，compileJava + build 通过；FG6 模板）
1.21.10→1.21.8 主要差异（1.21.10 引入的新渲染状态系统在 1.21.8 尚不存在）：
- **方块实体渲染器 API**：1.21.10 用 `BlockEntityRenderer<T, S extends BlockEntityRenderState>`（双泛型）+ `extractRenderState`/`submit` + `SubmitNodeCollector` + `CameraRenderState`；1.21.8 回退传统 `BlockEntityRenderer<T>`（单泛型）+ `render(T, float, PoseStack, MultiBufferSource, int, int, Vec3)`。`StatueBlockEntityRenderer` 与 `MiniStructureRenderer` 全部重写为传统 `render` 方法。
- **实体渲染**：1.21.8 的 `EntityRenderer` 已用 `EntityRenderState`，但 `render(S, PoseStack, MultiBufferSource, int)` 用 `MultiBufferSource` 而非 `SubmitNodeCollector`；`EntityRenderDispatcher.render(S, x, y, z, PoseStack, MultiBufferSource, int)`；⚠️ `LivingEntityRenderer.setupRotations(S, PoseStack, float bodyRot, float scale)` 是 **4 参（第 4 参就是 scale）**：反射调用必须按 4 参查找并传 `state.scale`——按 3 参查找会静默失败，模型完全不旋转，导致"雕像朝向不生效"（1.21.8/1.21.5 均已踩坑修复，invokeSetupRotations 现按 4 参查找、3 参兜底）；`model.setupAnim(S)`；`RenderLayer.render(PoseStack, MultiBufferSource, int, S, float, float)`。
- **SpecialModelRenderer**：`render(T, ItemDisplayContext, PoseStack, MultiBufferSource, int, int, boolean)`（无 `SubmitNodeCollector`、无 outlineColor）；`Unbaked.bake(EntityModelSet)` 而非 `bake(BakingContext)`。

## 九、单次构建同时产出 Forge + NeoForge（多加载器架构探索）

### 9.1 结论：可行，但不能"一个源码目录直接打两个包"
社区主流方案就是 **Architectury Loom + Gradle 多模块**：根目录执行一次 `./gradlew build`，Gradle 依次编译 `common → forgelike → forge/neoforge`，最终在 `forge/build/libs/` 与 `neoforge/build/libs/` 各得一个 jar。

但有两个必须正视的前提：
1. **common 只能放"加载器无关"的代码**。本模组 57 个 Java 文件中有 **24 个直接 `import net.minecraftforge.*`**（注册 9 个、事件 11 个、网络 10 个、配置/菜单/客户端若干），当前源码不能原样塞进 common。
2. Architectury 官方对"Forge 与 NeoForge 共享平台代码（forgelike）"有明确警告：**需要手工配置 NeoForge 类名 remap，非平凡且易崩**；更稳妥的终极形态是 common + 两套独立适配层（forgelike 只是过渡优化）。([官方迁移文档](https://docs.architectury.dev/loom/neoforge_migration/))

### 9.2 推荐目标结构（4 模块）
```
petrification-multiloader/
├─ settings.gradle              # include common / forgelike / forge / neoforge
├─ build.gradle                 # 只放插件与公共配置（apply false）
├─ gradle.properties            # MC/Forge/NeoForge/Architectury 版本
├─ common/                      # ★ 共享逻辑与资源（不依赖任何加载器）
│  ├─ build.gradle
│  └─ src/main/java + resources
├─ forgelike/                   # ★ 平台适配代码（用 Forge API 写，构建 NeoForge 时自动 remap）
│  ├─ build.gradle
│  └─ src/main/java
├─ forge/                       # Forge 入口（@Mod、mods.toml、事件总线绑定）
│  ├─ build.gradle
│  └─ src/main/{java,resources/META-INF/mods.toml}
└─ neoforge/                    # NeoForge 入口（@Mod、neoforge.mods.toml）
   ├─ build.gradle
   └─ src/main/{java,resources/META-INF/neoforge.mods.toml}
```
- **common**：`component/`、`data/`、`util/`（去掉 Forge 部分的）、`block/`、`item/`、`menu/`、`command/` 等业务逻辑，以及 `assets/`、`data/` 资源，全部与加载器无关。
- **forgelike**：注册（`DeferredRegister`/`RegistryObject`）、事件监听、网络通道、配置 `ForgeConfigSpec`、`IForgeMenuType`、客户端渲染注册等。写一次，两平台共用。
- **forge / neoforge**：只保留入口类（`@Mod` 构造器）、`mods.toml` / `neoforge.mods.toml`、平台差异实现（`@ExpectPlatform` 的落地方法）。

### 9.4 本模组的平台抽象层清单（按现有 Forge 依赖盘点）
| 现 Forge 依赖点 | 文件数 | 建议抽象 | NeoForge 对应 |
|---|---|---|---|
| `DeferredRegister`/`RegistryObject`/`ForgeRegistries` | 9 | `RegistryPlatform`（register* 系列） | `net.neoforged.neoforge.registries.DeferredRegister`/`DeferredHolder` |
| `IEventBus`/`@SubscribeEvent`/Forge 事件 | 11 | `PlatformEvents` 或放在 forgelike | `net.neoforged.bus.api.IEventBus` |
| `ChannelBuilder`/`PayloadFlow`/`CustomPayloadEvent` | 10 | `NetworkPlatform.sendToServer/sendToClient` | `PayloadRegistrar` + `IPayloadContext` |
| `ForgeConfigSpec`/`ModConfig` | 2 | `ConfigPlatform` | `ModConfigSpec` |
| `IForgeMenuType`/`IContainerFactory` | 2 | `MenuPlatform` | `IMenuTypeExtension` |
| `EntityRenderersEvent`/`RegisterColorHandlersEvent`/`FMLClientSetupEvent` | 3 | `ClientPlatform` | 同名事件在 `net.neoforged.neoforge.client.event` |
| `FMLEnvironment.dist`/`Dist.CLIENT` | 2 | `EnvPlatform.isClient()` | `FMLEnvironment.dist`（同名不同包） |
| `ForgeConfigSpecHolder` + 各注册类 | 24 | 整体迁入 forgelike | — |

Architectury 的 `@ExpectPlatform` 适合"一个方法两平台实现"的小差异；注册/事件这类大块建议直接放 forgelike，避免 common 里出现平台分支。

### 9.5 一次构建的产物与命令
```bash

# 产物：
#   forge/build/libs/petrification-2.1.0-forge.jar
#   neoforge/build/libs/petrification-2.1.0-neoforge.jar
```

### 9.6 风险与限制（务必先对齐预期）
1. **一次构建 ≠ 一个 jar 通吃**：仍产出两个 jar；且一次构建只对应**同一个 MC 版本**的 Forge + NeoForge。
2. **forgelike 的 remap 是最大坑**：`IForgeItem→IItemExtension` 等类名/包名差异要逐条声明，漏一条就是运行期 `NoClassDefFoundError`；官方明确"not recommended"。
3. **元数据不同**：Forge 用 `META-INF/mods.toml`，NeoForge 用 `META-INF/neoforge.mods.toml`（1.20.5+ 起）。
4. **API 版本越新差异越大**：1.21.1 的 Forge 52 与 NeoForge 21.1 高度同源，forgelike 可行性最高；26.x 两平台已明显分叉，建议 common + 两套适配层。
5. **Architectury API 前置**：若使用 `dev.architectury:architectury`，玩家必须额外安装 Architectury API；不装则无法启动。
6. **资源包 `pack_format`** 由 MC 版本决定，与加载器无关；同一 MC 版本下 common 资源可共用。
7. **本工程当前 14 个 MDK 的"逐版本编译"模式仍应保留**：多加载器工程是另一条交付线，不应破坏已验证的单加载器产物。

### 9.7 建议落地顺序（分阶段，低风险）
1. 选定基线：建议 **1.21.1**（Forge 52 / NeoForge 21.1 API 最接近，且本仓库该版本已移植）。
2. 用官方[模板生成器](https://generate.architectury.dev/)生成 `common/forgelike/forge/neoforge` 骨架，先跑通空模组双端 `runClient`。
3. 迁移 common：先搬 `component/`、`data/`、`util/` 中无 Forge import 的部分，再搬 `block/`、`item/`、`menu/`。
4. 抽取 `RegistryPlatform`/`NetworkPlatform`/`ConfigPlatform`/`MenuPlatform`/`ClientPlatform`/`EnvPlatform`，forgelike 提供 Forge 实现，neoforge 只处理差异。
5. 迁移 24 个 Forge 耦合文件到 forgelike，逐类解决 remap 清单。
6. 双端 `runClient` 冒烟 + `build` 校验两个 jar 的元数据与资源。
7. 通过后再评估是否回填 26.x 版本。

### 9.8 备选方案对比
| 方案 | 一次构建出 Forge+NeoForge | 额外运行时前置 | 维护成本 | 适用 |
|---|---|---|---|---|
| Architectury Loom + forgelike（本文） | ✅ | Architectury API（可选） | 中 | 两平台 API 接近（1.21.1） |
| Architectury Loom + common + 双适配层 | ✅ | Architectury API（可选） | 中高 | 26.x 等分叉较大的版本 |
| MultiLoader-Template（无 Architectury API） | ✅ | 无 | 高（胶水多） | 想零前置、同时支持 Fabric |
| 维持现状：每版本独立 MDK | ❌（各构建各的） | 无 | 低 | 当前降级移植交付线 |
